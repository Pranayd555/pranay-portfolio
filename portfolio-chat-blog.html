Building Eva: How I Shipped a Grounded, Real-Time AI Chat Assistant on My Portfolio

A first-person walkthrough of the engineering journey behind my portfolio's intelligent chat console — from deterministic function calling to Gemini Live streaming, containerized on a VPS behind Nginx.

Author: Pranay Das Stack: Node.js 22 · Express 5 · TypeScript · Gemini Live · Docker Assistant: Eva

The “Why” & The Problem

I started this project because I wanted something more than a static portfolio. I wanted an intelligent, knowledge-base-driven AI calling system embedded directly into my personal site — a system that could answer questions about my experience, projects, and technical decisions with the precision of a well-prepared interview, available at 2 AM when no recruiter is online to take a call.

The user experience problem was obvious once I started watching how people actually used my portfolio. Visitors are busy. They don’t have time to scroll through every project card, every skills badge, every case study paragraph, hunting for the one detail they care about. A recruiter wants to know about my Angular migration work. A founder wants the Presmistique architecture story. A fellow developer wants the CKEditor deep dive. They all land on the same page, but they all need different slices of the same data.

A chat console solves that instantly. Instead of navigating, they ask. Instead of guessing, they get the exact data they care about — pulled from a curated knowledge base I control.

The same pattern applies far beyond personal portfolios. Any company platform — internal docs, HR policies, product onboarding, support portals — benefits from an intelligent chat system that guides users according to company policies and instructions, not generic internet knowledge. I built Eva as a proof of concept for that broader idea, scoped tightly to my own professional narrative.

But here was the engineering constraint that kept me up at night: the agent had to be trained on particular data and tasks. It must not hallucinate. It must not provide false, imaginative, or confidently invented responses. On a personal portfolio, a single fabricated project detail is worse than no chat at all. I needed deterministic grounding — not a creative writing engine wearing a chat widget.

That constraint shaped every architectural decision that followed.

Phase 1

Deterministic AI with Function Calling & Token Optimization

My first approach was a classic request/response pattern: a POST endpoint on Express that accepted a user message, called the Gemini API, and returned a structured answer. I wired up an Express router for it — you can still see the skeleton in my codebase today, commented out in chat.routes.ts, a fossil from the first iteration:

That POST flow worked. But “worked” and “worked well” are different things. The real breakthrough in Phase 1 wasn’t the HTTP method — it was function calling.

The anti-hallucination strategy

Instead of stuffing my entire résumé into a system prompt and hoping the model wouldn’t invent details, I gave the model a single tool: searchKnowledge. The system prompt I wrote is aggressive about boundaries — no world knowledge, no inference, no guessing, no fabrication. Tool results are the sole source of truth.

src/services/gemini.service.tsSystem prompt & tool definition
const SYSTEM_PROMPT = `
You are Eva.

You may ONLY answer using information returned by the searchKnowledge tool.

If a question requires information not present in tool results:

"I couldn't find information about that in Pranay's portfolio knowledge base."

If a question is unrelated to Pranay Das:

"I'm designed exclusively to discuss Pranay Das, his experience, projects, skills, and professional work. Please ask a relevant question."

Do not answer from your own knowledge.
Do not use world knowledge.
Do not infer.
Do not guess.
Do not fabricate.
Do not provide general assistance.

Use searchKnowledge whenever information is needed.

Tool results are the sole source of truth.
`;

const searchKnowledgeTool: FunctionDeclaration = {
  name: "searchKnowledge",
  description: "Retrieve information from Pranay's knowledge base",
  parametersJsonSchema: {
    type: 'object',
    properties: {
      source: {
        type: 'string',
        description: 'The exact knowledge source to read from.',
        enum: [
          'ckeditor5',
          'ngrx',
          'skills',
          'experience',
          'presmistique',
          'projects_overview',
        ],
      },
    },
    required: ['source'],
  },
};

The model doesn’t get to freestyle. It must plan which knowledge source to read, observe the returned content, and only then produce a final answer grounded in that observation. I surface this loop to the client as structured AGENT_STEP events — planning when the tool call is initiated, observation when the result is fed back to the model.

src/services/gemini.service.tsPlanning → Observation → Output loop
onmessage: async (message: any) => {
  if (message.toolCall?.functionCalls) {
    for (const call of message.toolCall.functionCalls) {
      onStep('planning', { message: `AI is planning to run tool: ${call.name}` });

      const result = await executeTool(call.name, call.args);

      onStep('observation', {
        message: 'Tool output received and fed back to model.',
        resultPreview: JSON.stringify(result).substring(0, 150) + '...'
      });

      await session.sendToolResponse({
        functionResponses: [{
          id: call.id,
          name: call.name,
          response: result,
        }]
      });
    }
  }

  if (message.serverContent?.modelTurn?.parts) {
    for (const part of message.serverContent.modelTurn.parts) {
      if (part.text) {
        onTextChunk(part.text);
      }
    }
  }
  // ...
}

Token optimization through document chunking

Early on, I tried dumping everything into one giant context window. Response times ballooned. Token costs climbed. The model got slower and noisier. So I broke my documentation into smaller, purpose-specific markdown files — one per knowledge domain — and let the model select only the file it needs via the source enum.

src/services/knowledge.service.tsChunked knowledge sources
private fileMap: Record<KnowledgeSource, string> = {
  ckeditor5: 'project_ckeditor_deepdive.md',
  ngrx: 'project_ngrx_deepdive.md',
  presmistique: 'project_presmistique_deepdive.md',
  projects_overview: 'projects_overview.md',
  skills: 'skills.md',
  experience: 'experience.md'
};

async getContent(source: KnowledgeSource): Promise<string> {
  if (this.cache.has(source)) {
    return this.cache.get(source)!;
  }

  const filePath = path.join(
    __dirname, '..', '..', 'src', 'knowledge', this.fileMap[source]
  );

  const content = await fs.readFile(filePath, 'utf8');
  this.cache.set(source, content);
  return content;
}

A question about my CKEditor work pulls project_ckeditor_deepdive.md — not the entire knowledge base. A skills question pulls skills.md only. Combined with an in-memory cache, repeat lookups within a session are essentially free. Smaller payloads, faster tool execution, lower token burn. This was one of those optimizations that felt obvious in hindsight but made a measurable difference in latency.

Phase 1 outcome: Eva answered from my data, refused to invent, and could explain which document it consulted. The POST API proved the concept. But users still waited for the full response to arrive before seeing anything. I wanted progressive output.

Phase 2

Upgrading to Real-Time Streaming with Gemini Live & WebSockets

Once the POST-based function-calling flow was solid, the UX gap became impossible to ignore. Users stared at a loading spinner while the model planned, retrieved, and composed — only then did the full answer appear. I wanted faster, progressive outputs. Token by token. Chunk by chunk. The way modern chat interfaces feel.

That’s when I discovered the Gemini Live API — a persistent, bidirectional session model designed for real-time interaction. I upgraded the architecture: instead of stateless POST round-trips, I opened a long-lived Gemini Live session per browser connection and bridged it to the frontend over WebSockets.

The model I landed on is gemini-3.1-flash-live-preview. I configure it with audio as the primary response modality, but enable outputAudioTranscription so the transcribed text streams back to my chat UI — giving visitors a familiar text experience without me having to pipe raw audio through a portfolio widget.

src/services/gemini.service.tsGemini Live session config
const model = "gemini-3.1-flash-live-preview";
const config = {
  responseModalities: [Modality.AUDIO],
  outputAudioTranscription: {},
  systemInstruction: SYSTEM_PROMPT,
  tools: [
    {
      functionDeclarations: [searchKnowledgeTool],
    },
  ],
};

export async function runPortfolioAgent(
  socketId: string,
  onTextChunk: (text: string) => void,
  onStep: (step: string, detail: any) => void,
  onTurnComplete: () => void
) {
  const session = await ai.live.connect({ model, config, callbacks: { /* ... */ } });
  return session;
}

Backend: Express + native WebSockets on one port

Express doesn’t handle WebSocket upgrades out of the box. I created a raw http.Server from my Express app and intercepted upgrade events before they hit Express routing. Origin verification happens at upgrade time — only origins listed in ALLOWED_ORIGINS get through. This keeps my Gemini API key safely server-side while my Angular portfolio on Cloudflare Pages connects as a trusted client.

src/server.tsHTTP upgrade → WebSocket handoff
const server = createServer(app);

server.on('upgrade', (request, socket, head) => {
  const { pathname } = new URL(request.url || '', `http://${request.headers.host}`);
  const origin = request.headers.origin || '';

  if (!env.allowedOrigins.includes(origin)) {
    console.warn(`WS upgrade rejected for origin: ${origin}`);
    socket.write('HTTP/1.1 403 Forbidden\r\n\r\n');
    socket.destroy();
    return;
  }

  if (pathname === '/api/chat') {
    chatWss.handleUpgrade(request, socket, head, (ws) => {
      chatWss.emit('connection', ws, request);
    });
  } else {
    socket.destroy();
  }
});

Each WebSocket connection gets a UUID, a dedicated Gemini Live session stored in a liveSessions map, and clean teardown on disconnect. When a visitor sends a message, I forward it into the live session via sendClientContent. When Gemini streams back text, I emit TEXT_CHUNK events. When a turn finishes, I emit TURN_COMPLETE.

src/controllers/chat.controller.tsSession bridge & message relay
const liveSessions = new Map<string, any>();

chatWss.on('connection', async (ws: WebSocket, request: IncomingMessage) => {
  const connectionId = randomUUID();

  const geminiSession = await runPortfolioAgent(
    connectionId,
    (textChunk) => {
      ws.send(JSON.stringify({ type: 'TEXT_CHUNK', text: textChunk }));
    },
    (step, detail) => {
      ws.send(JSON.stringify({ type: 'AGENT_STEP', step, detail }));
    },
    () => {
      ws.send(JSON.stringify({ type: 'TURN_COMPLETE' }));
    }
  );

  liveSessions.set(connectionId, geminiSession);

  ws.on('message', (message: string) => {
    const data = JSON.parse(message.toString());

    if (data?.type === 'USER_MESSAGE' && typeof data.text === 'string') {
      const session = liveSessions.get(connectionId);
      session.sendClientContent({
        turns: [{ role: 'user', parts: [{ text: data.text }] }],
        turnComplete: true,
      });
    }
  });

  ws.on('close', () => {
    const session = liveSessions.get(connectionId);
    if (session) {
      session.close();
      liveSessions.delete(connectionId);
    }
  });
});

Frontend: the WebSocket contract my Angular app consumes

My portfolio frontend is a separate Angular application hosted on Cloudflare Pages. It doesn’t live in this backend repo, but it speaks a strict JSON protocol that this server defines. On connect, Eva sends a branded WELCOME message. The client sends user input as:

Client → ServerJSON message
{
  "type": "USER_MESSAGE",
  "text": "Tell me about your Angular experience"
}

The server streams back typed events my Angular chat component handles:

Event Purpose
SYSTEMConnection status
WELCOMEBranded intro + connectionId
TEXT_CHUNKIncremental streamed text — appended live in the UI
AGENT_STEPTool-call progress (planning, observation)
TURN_COMPLETEModel finished its turn — re-enable input
ERRORParse failures, missing session, connection errors

On the frontend, I open a native WebSocket to wss://<api-host>/api/chat, subscribe to incoming events, append each TEXT_CHUNK to the current assistant message bubble, toggle a thinking indicator on AGENT_STEP with step: 'planning', and auto-scroll the message list on every chunk. Input is disabled until TURN_COMPLETE arrives.

Why persistent sessions matter: Because the Gemini Live connection stays open for the entire chat, follow-up questions reuse established context. “Tell me more about that CKEditor project” after an initial skills question is dramatically faster — the session already exists, the knowledge was already retrieved, and the model doesn’t cold-start from zero every turn.

Phase 3

Containerization & VPS Deployment

Local development was smooth. Production needed to be boring — predictable, reproducible, and environment-agnostic. I packaged the entire backend into a multi-stage Docker image and deployed it on an InterServer VPS, fronted by Nginx as a reverse proxy to handle SSL termination and route both HTTP health checks and WebSocket upgrade traffic from Cloudflare.

Multi-stage Dockerfile

The build stage compiles TypeScript. The runtime stage ships only production dependencies and compiled output. Critically, markdown knowledge files aren’t compiled by tsc — so I copy them explicitly into the runtime image at a path my KnowledgeService resolves at startup.

DockerfileMulti-stage build
# Build stage
FROM node:22-alpine AS builder

WORKDIR /app

COPY package*.json ./
RUN npm ci

COPY . .
RUN npm run build

# Runtime stage
FROM node:22-alpine

WORKDIR /app

COPY package*.json ./
RUN npm ci --omit=dev

COPY --from=builder /app/dist ./dist

# Copy the static knowledge folder into the runtime image
COPY --from=builder /app/src/knowledge ./src/knowledge

EXPOSE 3000

CMD ["npm", "start"]

Docker Compose

On the VPS, a single docker compose up --build -d brings everything online. Environment secrets come from a .env file on the host — API keys never get baked into the image layers.

Nginx reverse proxy (production)

Nginx sits between Cloudflare and my Docker container. Standard HTTP proxying handles the health endpoint. WebSocket upgrades require explicit Upgrade and Connection headers, plus an extended read timeout — Gemini Live sessions are long-lived and default Nginx timeouts will kill them.

/etc/nginx/sites-available/portfolio-apiRepresentative config
server {
    listen 443 ssl http2;
    server_name api.yourdomain.com;

    # SSL certs (or Cloudflare origin cert)
    ssl_certificate     /etc/ssl/certs/origin.pem;
    ssl_certificate_key /etc/ssl/private/origin.key;

    location /api/health {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /api/chat {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
    }
}

The final production topology:

Visitor Browser │ ▼ Cloudflare (CDN + DNS + Pages frontend) │ ├──▶ Cloudflare Pages ──▶ Angular portfolio (static) │ └──▶ InterServer VPS │ ▼ Nginx (SSL + reverse proxy) │ ▼ Docker Compose │ ▼ portfolio-backend-runtime :3000 │ ▼ Gemini Live API + Markdown KB

Lesson learned: The knowledge path resolution in Docker was a gotcha. TypeScript compiles to dist/, but .md files don’t compile. My KnowledgeService resolves paths relative to src/knowledge/ at runtime, and the Dockerfile explicitly copies that directory. Without that copy step, Eva would connect fine but every tool call would fail silently on missing files.

Key Takeaways & Conclusion

Building Eva changed how I think about portfolio interactivity. A static site tells your story. A grounded, real-time AI agent participates in the conversation about your story — on your terms, with your data, under your constraints.

Three principles carried me through:

  1. Ground before you generate. Function calling with a strict system prompt and chunked knowledge files eliminated hallucination as a category of bug — not just reduced its likelihood.
  2. Stream before you wait. Gemini Live over WebSockets turned a functional chat into a feelable one. Progressive TEXT_CHUNK delivery and persistent session context made follow-up queries snappy.
  3. Containerize before you deploy. Docker + Compose on a VPS with Nginx in front gave me a production setup I can reproduce on any machine with a single command.

The same architecture scales beyond portfolios. Any platform that needs to guide users according to specific policies, documentation, or product knowledge — without inventing answers — can adopt this pattern: chunked knowledge sources, tool-gated retrieval, strict system instructions, real-time streaming, and containerized deployment behind a reverse proxy.

Real-time AI agents are not a gimmick on a personal website. They are a new interaction layer — one where visitors don’t browse, they ask. And when the agent is built right, every answer is yours.

If you’re a developer considering this for your own portfolio or product, start with the constraint: what must the agent never get wrong? Build the guardrails first. The streaming UX and Docker deployment are the rewarding parts — but the grounding is what makes the whole thing trustworthy.
