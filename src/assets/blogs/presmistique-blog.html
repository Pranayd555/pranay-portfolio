Building a Full-Stack Resume Builder: Architecture, Trade-offs, and Real-World Challenges

I built a production-ready resume builder with token-based AI features, Razorpay payments, and a sophisticated refund system. This post covers the real decisions, mistakes, and lessons learned along the way.

Introduction: Why I Built This

The idea originated from a practical observation: a rich text editor can already generate structured HTML, which means it should be possible to design resumes visually and export them reliably as PDF or Word documents. But once I started implementing this, I hit a fundamental issue — rendering consistency across formats.

warning Core insight

HTML rendering in an editor context is not equivalent to document rendering for export. This exposed a deeper challenge involving layout fidelity, data modelling, and rendering pipelines.

I also wanted to deepen my understanding of full-stack development. The stack I chose deliberately:

  • React.js — building a highly dynamic and state-driven UI
  • Node.js + Express — scalable and modular backend
  • MongoDB Atlas — flexible handling of user-generated resume data

Beyond just a resume editor, the goal evolved into designing a system that maintains consistency between editing and exported output, handles variable user-generated data, integrates AI features, and supports production concerns like payments, concurrency, and deployment.

What Problem Does This Actually Solve?

Let me be real: there are dozens of resume builders out there. But the ones I found either lock basic features or add paywalls at every step.

block Traditional approach

Free with aggressive paywalls. Let you create a resume, then hit you with "Premium unlock?" at every step.

check_circle My approach

Lean on AI for the hard part (parsing + suggestions), charge for tokens (AI actions), not basic features. Users can create unlimited resumes for free.

This changes the monetisation entirely. Instead of nickel-and-diming users, you're selling actual value.

Key decision: loose validation on resume fields

Users have weird data. Someone might not have a phone number, or have 20 jobs, or skip education entirely. Strict schema validation would've been a nightmare. Trade-off: the frontend has to do most validation. I spent extra time on client-side validation to prevent garbage data reaching the database.

Implementation Highlights

1. Payment Flow & Signature Verification

Razorpay requires signature verification to prevent tampering. Someone could theoretically intercept the API call and change the amount from ₹100 to ₹1 if we didn't verify. Here's the complete purchase flow: 

// Complete purchase with signature verification
router.post('/complete-token-purchase', protect, async (req, res) => {
  const { order_id, payment_id, signature, tokens, amount } = req.body;

  // CRITICAL: Verify signature (prevents tampering)
  const body = order_id + '|' + payment_id;
  const expectedSignature = crypto
    .createHmac('sha256', process.env.RAZORPAY_KEY_SECRET)
    .update(body.toString())
    .digest('hex');

  if (expectedSignature !== signature) {
    logger.error(`Signature mismatch for payment ${payment_id}`);
    return res.status(400).json({
      success: false,
      message: 'Invalid payment signature'
    });
  }

  // Double-check with Razorpay API
  const payment = await razorpay.payments.fetch(payment_id);
  if (payment.status !== 'captured') {
    return res.status(400).json({
      success: false, message: 'Payment not captured'
    });
  }

  // Check if already processed (prevent duplicates)
  const existingTransaction = user.getTransactionById(payment_id);
  if (existingTransaction) {
    return res.status(400).json({
      success: false, message: 'Payment already processed'
    });
  }

  // Add tokens to user
  user.tokens += tokens;
  await user.save();
});

I also added duplicate payment protection. Early testing showed it's possible for a user to submit the same payment twice by accident (network lag, double click, etc.).

2. The Refund System (The Complex Part)

Refunds need to account for token usage, bonus tokens, and fairness. I implemented 6 different refund scenarios:

1 No bonus, all tokens unused → 100% refund
2 No bonus, some tokens used → Partial refund
3 With bonus, all tokens intact → 100% refund
4 Bonus partially used, purchased intact → Partial refund
5 Calculated refund below minimum threshold → Not eligible
6 Complex mixed scenario → Partial refund for effective remaining tokens 
class RefundCalculator {
  static calculateRefund(transaction, currentUserState, paidAmount) {
    const { tokens: currentTokens, bonusTokens: currentBonusTokens } = currentUserState;
    const { boughtTokens, bonusTokensAdded } = transaction.metadata;

    // Scenario 1: No bonus, all tokens unused
    if (!bonusTokensAdded && currentTokens >= boughtTokens) {
      return { scenario: 1, refundAmount: paidAmount, refundPercentage: 100, status: 'eligible' };
    }

    // Scenario 2: No bonus, some tokens used
    if (!bonusTokensAdded && currentTokens < boughtTokens) {
      const refundAmount = Math.round((paidAmount / boughtTokens) * currentTokens);
      return { scenario: 2, refundAmount, status: 'eligible' };
    }

    // ... (scenarios 3-6 handle bonus token combinations)
  }
}

4. Rate Limiting & AI Token Consumption

AI API calls are expensive. Token deduction happens before the API call. And to prevent race conditions (user opens multiple tabs, sends parallel requests), I used MongoDB transactions: 

// Use session for atomicity
const session = await mongoose.startSession();
session.startTransaction();

try {
  const user = await User.findById(req.user.id).session(session);
  if (user.bonusTokens + user.tokens <= 0) {
    await session.abortTransaction();
    return res.status(403).json({ error: 'No tokens' });
  }

  // Deduct token atomically
  await User.updateOne(
    { _id: req.user.id },
    { $inc: { bonusTokens: -1 } },
    { session }
  );

  await session.commitTransaction();
} finally {
  session.endSession();
}
If the AI call fails after deduction, the token is refunded in the catch block. This prevents users losing tokens due to upstream API errors.

Challenges & How I Solved Them

bug_report Challenge 1: Deployment Hell (Render Zip File Issues)

I spent 8 hours debugging why deployment was failing. Render requires a zip file upload — my build script's .npmrc conflicted with Render's own copy.

  • Just delete .npmrc before zipping ❌ (Render still had its copy)
  • Use -o flag in unzip ❌ (some unzip versions don't support it)
  • Recreate .npmrc after unzip ❌ (timing / race condition)

What actually worked: A custom Node.js build script using archiver that explicitly deletes .npmrc before creating the archive, then adds only the explicit directories and files needed. No ambiguity.

security Challenge 2: JWT Token Refresh & Session Management

Managing sessions across multiple devices is hard. I needed refresh tokens without hitting the database on every request.

Solution: Refresh tokens with sliding expiration. The middleware checks if a token expires within 24 hours and, if so, issues a new one via the X-New-Token response header. The frontend checks for this header and updates local storage — zero extra database round-trips. 

// If less than 1 day left, issue new token silently
const timeUntilExpiry = (decoded.exp * 1000) - Date.now();
if (timeUntilExpiry < 24 * 60 * 60 * 1000) {
  const newToken = jwt.sign(
    { id: req.user._id },
    process.env.JWT_SECRET,
    { expiresIn: '7d' }
  );
  res.set('X-New-Token', newToken);
}

Performance & Optimisations

speed Template Caching

Handlebars rendering on large resumes was slow (2–3 seconds). Caching compiled templates dropped it to ~200ms. 

const templateCache = {};

function getCompiledTemplate(templateName) {
  if (templateCache[templateName]) {
    return templateCache[templateName]; // cache hit
  }
  const source = fs.readFileSync(`./templates/${templateName}.hbs`, 'utf-8');
  templateCache[templateName] = Handlebars.compile(source);
  return templateCache[templateName];
}
Before: 2–3 s arrow_forward After: ~200 ms

database Database Indexing

Querying resumes by user was slow early on. Two targeted indexes fixed it. 

resumeSchema.index({ user: 1, createdAt: -1 });
resumeSchema.index({ user: 1, updatedAt: -1 });

What I'd Do Differently

  • Start with Auth Earlier. I built the resume builder first, then added auth. Mistake. Auth affects database schema, API design, and frontend routing — set it up on day 1.
  • Design the Payment System Before Implementation. I designed the refund logic retroactively, which meant refactoring the User model twice. Sketch all business logic before writing any backend code.
  • Better Error Handling from Day 1. Specific status codes, error codes the frontend can act on, proper logging, and user-friendly messages — not "Something went wrong".
  • Write Tests Earlier. I didn't write tests until month 4. By then there were 50+ routes and 200+ functions. Tests would've saved hours of manual testing.
  • Document Deployment Step-by-Step. If I'd documented each step as I went, I'd have saved that 8-hour debugging session.

Key Learnings

Signature Verification Matters

I almost shipped without Razorpay signature verification. That's a massive security hole. Always verify signatures.

Transactions Are Worth The Overhead

MongoDB transactions seemed overkill. But once token deduction became critical, they were essential for correctness.

Flexible Schema > Strict Schema

Resumes are inherently messy. Loose schema + frontend validation = happier development.

Logging Is Better Than Guessing

Adding Winston logging was a game-changer. Now I can see exactly what failed in production and why.

Token Monetisation Is Cleaner

Selling tokens for AI actions is less intrusive than feature paywalls and feels more fair to users.

Race Conditions Are More Common Than Expected

Sessions, transactions, and atomic operations aren't nice-to-have — they're essential in any multi-tab app.

Conclusion

Building Resume Builder taught me that production-ready code is 70% implementation and 30% deployment, security, and edge cases. The refund system, payment verification, and token deduction logic took longer than the core resume builder — but they're what separates a side project from a product users trust.

If you're building a SaaS, spend more time on:

  • Security — verify everything
  • Transactions — prevent race conditions
  • Error handling — log everything
  • Deployment — test multiple times

The sexy code is the least important part.
