Replacing CKBox with “just S3”: my CKEditor 5 migration war story (Angular 13 → 14)

This project didn’t start as “let’s build a fancy editor.” It started as an Angular 13 → Angular 14 migration where one dependency quietly turned into a whole subplot: CKEditor 4 → 5 meant rethinking file management, and I didn’t want the migration to turn into “editor upgrade + paid storage product rollout.”

Angular migration CKEditor 5 S3 / R2 Custom plugin File manager UX

Context: why this project exists at all

We were moving Angular 13 → Angular 14, and that upgrade forced a bigger dependency change: CKEditor 4 → CKEditor 5.

warning Where it got messy

  • In CKEditor 4, we had an Amazon S3 flow that was basically “free + configurable,” and it matched the rest of our stack (we were already AWS-heavy).
  • In CKEditor 5, the “official” file management story is typically CKBox or CKFinder.
  • Both are good products, but for our situation they were a bad fit: paid, and also a new storage workflow in an app that already has S3 everywhere.

Problem statement

“How do we migrate to CKEditor 5 and keep the S3-based asset workflow we already rely on—without introducing CKBox/CKFinder cost and without regressing editor features?”

This repo is my answer: a custom CKEditor 5 bundle with a custom S3/R2 file manager plugin, designed to preserve the “browse/upload/reuse assets” workflow we had before.

What the project solves (in plain terms)

I ended up building a custom CKEditor 5 bundle that includes a custom S3 file manager plugin:

extension A CKEditor 5 plugin

  • Sets up an S3-compatible client (AWS S3 or Cloudflare R2)
  • Registers a browse command (s3Browse)
  • Hooks into the upload pipeline via FileRepository.createUploadAdapter

folder_open A “File Manager” modal

  • Lists folders + files in the bucket
  • Lazy-loads image previews using signed URLs
  • Supports CRUD operations (create folder, upload, delete)
  • Inserts assets into the editor (images immediately; audio supported via a model element)

In the editor toolbar, it shows up as a s3Browse action: 

toolbar: {
  items: [
    'undo',
    'redo',
    // ...
    'indent',
    '|',
    's3Browse',
  ],
  shouldNotGroupWhenFull: true
},

It’s not a generic “tutorial plugin.” It’s a practical “this is what I needed to ship the migration” solution.

Architecture & key decisions (and the trade-offs I actually weighed)

Decision 1: “Don’t pay for CKBox/CKFinder; build around S3”

I didn’t avoid CKBox/CKFinder because they’re bad. I avoided them because they didn’t match the reality of the project:

  • Cost: hard to justify when S3 is already paid for and already integrated.
  • Workflow mismatch: the app already understands buckets/keys/folders/policies.
  • Migration scope: I wanted this to be “editor migration,” not “editor + new vendor rollout.”

Trade-off: I took on real engineering responsibility (UX + security + storage concerns) that CKBox/CKFinder normally absorbs for you.

Decision 2: “It had to be JavaScript, because the editor source is JavaScript”

At the time, most of the CKEditor “custom plugin” docs/examples I could follow were JavaScript-first. So this wasn’t “JS vs TS ideology.” It was:

  • Write the plugin/editor in JS, the way the docs were showing it, so I wasn’t translating concepts and debugging build issues at the same time.
  • Integrate the built output into the Angular/TypeScript app as an artifact, instead of trying to make CKEditor internals TypeScript-native inside Angular’s build.

Trade-off: I gave up type safety inside the plugin code, and I had to be more disciplined about runtime checks and error handling.

Decision 3: “Bundle the editor so other apps can consume it”

The moment the plugin worked locally, the next problem was: how do I ship it into an existing application cleanly? Webpack output solved that by producing a consumable editor bundle. 

output: {
  library: 'ClassicEditor',
  libraryTarget: 'umd',
  libraryExport: 'default',
  umdNamedDefine: true,
  path: path.resolve(__dirname, 'build'),
  filename: 'ckeditor.js',
},

Trade-off: now I’m maintaining a build pipeline specifically for the editor bundle. But it kept the Angular app build from turning into a CKEditor build science project.

The architecture: how the system is structured

Components:

  • src/ckeditor.js defines the custom editor build + toolbar config.
  • src/fileManagerPlugin.js wires everything together.
  • src/S3BrowseCommand.js renders the modal UI and performs storage operations.
  • src/S3UploadAdapter.js implements the upload adapter for the insert-image pipeline.

Happy path: how the plugin works (high level)

  1. 1 Editor boots with the custom bundle
  2. 2 You load the custom CKEditor build (build/ckeditor.js) which already includes AmazonS3Plugin.
  3. 3 Plugin initializes and wires storage + commands
  4. 4 On init(), the plugin creates an S3-compatible client (AWS S3 or Cloudflare R2 endpoint). It registers:
    • a custom upload adapter via FileRepository.createUploadAdapter (for the editor’s image insert pipeline)
    • a command s3Browse (the file manager entrypoint)
  5. 5 User clicks “Browse” in the toolbar
  6. 6 CKEditor executes the s3Browse command. The command opens a modal “File Manager” UI.
  7. 7 Modal loads folders and the first folder’s contents. It lists folders using ListObjectsV2 with Delimiter: '/'. It lists the selected folder’s contents using Prefix: '<folder>/'. Results are cached briefly to avoid hammering the API while the user clicks around.
  8. 8 UI renders quickly, previews load lazily. The file grid renders immediately with placeholders.
  9. 9 For images, the command generates signed URLs (getSignedUrl + GetObjectCommand) and swaps them into <img> tags after render.
  10. 10 User uploads images into the selected folder. The modal’s “Upload” button opens a file picker (restricted to png/jpg/jpeg). Files are validated (size/type). If too large, the user can opt to compress. Upload happens via PutObjectCommand to Bucket + Key: '<folder>/<filename>'. Cache is invalidated and the UI refreshes so the new files show up immediately.
  11. 11 User inserts an asset into the editor. Clicking an image generates a signed URL and calls editor.execute('insertImage', { source: signedUrl }). Clicking an audio file creates an audio model element with src set to the signed URL (and the plugin defines how it downcasts to an <audio> tag in the output).
  12. 12 User deletes a file or a folder. Delete file: DeleteObjectCommand, then refresh. Delete folder: list keys under the prefix and bulk delete with DeleteObjectsCommand, then refresh.

Implementation highlights (real code, real reasoning)

1) Wiring the plugin into CKEditor (commands + upload adapter)

This is the “entry point” where the plugin becomes real: create a client, register an upload adapter, add the browse command. 

init() {
  // connect cloudflare R2
  this.s3Client = new S3Client({
    region: "auto",
    endpoint: process.env.R2_API || 'https://<ACCOUNT_ID>.r2.cloudflarestorage.com',
    signatureVersion: 'v4',
    credentials: {
      accessKeyId: process.env.R2_ACCESS_KEY_ID || '',
      secretAccessKey: process.env.R2_SECRECT_ACCESS_KEY || ''
    },
  });

  // Register upload adapter for insertImage functionality
  this.editor.plugins.get('FileRepository').createUploadAdapter = (loader) => {
    return new S3UploadAdapter(loader, this.s3Client, bucketName);
  };

  // Add commands
  this.editor.commands.add('s3Browse', new S3BrowserCommand(this.editor, this.s3Client));
}

Why this matters: this is the line between “some storage code” and “a real CKEditor feature.” Commands + upload adapters are the extension points CKEditor expects you to integrate with, so once I aligned with those, everything else became easier to reason about.

2) File manager performance: don’t download objects for previews

My early model was “List objects → fetch objects → show previews.” It works… until it doesn’t. It’s slow, heavy, and makes the UI feel broken. The better approach:

  • List keys with ListObjectsV2
  • Generate signed URLs for previews
  • Lazy-load previews after UI render
const command = new ListObjectsV2Command({
  Bucket: bucketName,
  Prefix: folderName + "/",
  Delimiter: "/",
});

const { Contents } = await this.s3Client.send(command);

// Process files WITHOUT downloading them (major optimization)
const updatedContents = Contents
  .map((item) => {
    const parts = item.Key.split("/");
    const fileName = parts[parts.length - 1];
    if (!fileName.length) return null;
    return {
      ...item,
      fileName,
      // Mark if needs preview, but don't download yet
      needsPreview: this.isImageFile(fileName)
    };
  })
  .filter(item => item !== null);

async getImagePreviewUrl(fileKey) {
  const command = new GetObjectCommand({
    Bucket: bucketName,
    Key: fileKey,
  });
  // Use signed URL instead of downloading - much more efficient
  return await getSignedUrl(this.s3Client, command, { expiresIn: 3600 });
}

Trade-off: signed URLs add complexity (expiry, caching, permissions). But for a file manager UI, they’re worth it: the browser handles loading/decoding efficiently and your JS thread doesn’t become a download pipeline.

3) UX constraints that match real teams: limits + guardrails

This plugin isn’t trying to be “S3 Explorer.” It’s trying to preserve a workflow safely during a migration, so I enforced practical constraints:

  • Restrict upload file types
  • Enforce size targets and offer compression
  • Cap how many files can be uploaded per folder (predictable UX + performance during rollout)

That’s not theoretical purity—that’s “this keeps the experience stable while migrating.”

Challenges (the stuff that actually slowed me down)

“CKEditor 5 plugin development has constraints you only learn by bleeding”

CKEditor doesn’t behave like a normal frontend framework. It has its own concepts (commands, conversion, model/view pipelines), and when you do something slightly wrong you can get errors that aren’t obviously connected to the bug.

  • Staying close to docs/examples (JS-based back then)
  • Building a minimal skeleton first (button → command → modal)
  • Only then layering storage calls, caching, and UX polish

“CORS isn’t a footnote, it’s a project requirement”

The moment you upload/delete from the browser, CORS becomes non-negotiable. I had to treat it as part of “making the plugin work,” not “deployment detail.”

Here’s an example CORS policy (R2 or S3) that unblocks local development: 

[
  {
    "AllowedOrigins": [
      "http://localhost:8080"
    ],
    "AllowedMethods": [
      "GET",
      "PUT",
      "POST",
      "DELETE",
      "HEAD"
    ],
    "AllowedHeaders": [
      "*"
    ]
  }
]

“Integrating into another application is its own challenge”

Even after the plugin worked, I still had to answer: “How does Angular consume this without chaos?” That’s where bundling became the practical bridge.

How someone can actually use it

At a high level, it’s:

  • Build the custom editor bundle with webpack.
  • Host the sample (or import the built artifact into another app).
  • Configure bucket + CORS.
  • Use the toolbar button to browse/upload/insert.

What I’d do differently

  • Security/auth: move away from long-lived credentials in the browser and use server-minted temporary access or presigned URLs.
  • UI architecture: reduce reliance on global handlers for modal actions and tighten the event model.
  • Consistency: unify the “insert image” flow so everything ends up as stored objects + URLs (instead of sometimes base64).

None of those invalidate the project. They’re just the next steps if I were turning this from “migration solution” into a hardened library.

Key learnings (the practical kind)

  • Migrations expose hidden costs: Angular upgrades can force editor upgrades, which can force storage workflow decisions.
  • Paying for the official solution isn’t always the right call if it clashes with existing infra and cost constraints.
  • Performance is product in file managers—signed URLs + lazy previews changed everything.
  • Bundling matters: a working plugin isn’t “done” until it’s consumable in the real application.
