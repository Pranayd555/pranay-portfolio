NgRx in a Small Angular App: The Project That Finally Made It Click (for Me)

NgRx is one of those things I understood on paper for a while… but it didn’t really click until I built a small Angular app where the goal was simple: use NgRx properly, end-to-end, and see the whole flow working in a real UI.

So I built a “fruits” feature (load/add/update/delete) in Angular 16 and wired it with:

  • @ngrx/store for state
  • @ngrx/effects for HTTP side effects
  • @ngrx/store-devtools so I could actually see actions + state transitions while learning

This post walks through how I implemented it in the project, with the actual code.

Angular 16 NgRx Effects Learning flow

What the app does (and why it was perfect for learning NgRx)

The UI is straightforward:

  • Load and render a list of fruits from an API
  • Add a fruit
  • Update a fruit
  • Delete a fruit

It’s not trying to be clever. It’s the kind of feature that gets messy fast if everything lives inside components—and that’s exactly why it’s a good NgRx learning vehicle.

The NgRx flow I wanted was:

Component dispatches action → Effect calls API → Effect dispatches success/failure → Reducer updates store → Component renders from store

Step 1: Wire NgRx into Angular (store + effects + devtools)

In frontend/package.json, NgRx is included like this: 

"@ngrx/effects": "^16.3.0",
"@ngrx/store": "^16.3.0",
"@ngrx/store-devtools": "^16.3.0",

Then the store is registered in AppModule. I keep it simple: one slice called fruits, one reducer, one effects class. 

StoreModule.forRoot({ fruits: fruitReducer}),
StoreDevtoolsModule.instrument({ maxAge: 25, logOnly: !isDevMode() }),
EffectsModule.forRoot([FruitEffects]),

That’s the first milestone: after this, NgRx exists in the app and can start handling dispatched actions.

Step 2: Actions (turning UI events into explicit “intent”)

Actions were the first part of NgRx that changed how I structured code.

Instead of components directly calling services, the component “declares intent”:

  • “get fruits”
  • “add fruit”
  • “update fruit”
  • “delete fruit”

Those live in src/app/store/actions/fruits.action.ts.

Here’s the load actions: 

export const getFruits = createAction('[Fruit] get fruit');
export const getFruitsSuccess = createAction(
  '[Fruit] get fruit success',
    (fruits: ReadonlyArray<Fruit>) => fruits
);
export const getFruitsFailure = createAction(
    '[Fruit] get fruit failure',
  props<any>()
  );

And delete, which takes a payload: 

export const deleteFruits = createAction(
  '[Fruit] delete fruit',
    props<{name: string}>()
);
export const deleteFruitsSuccess = createAction(
  '[Fruit] detele fruit sucess',
  (fruits: ReadonlyArray<Fruit>) => fruits
);
export const deleteFruitsFailure = createAction('[Fruit] delete fruit failure');

What changed for me

Once I started treating actions as “messages” instead of “functions,” NgRx made more sense. It becomes much easier to reason about the app when every meaningful event is explicit and traceable.

Step 3: Reducer (pure state updates, nothing else)

Reducers were the part I had to discipline myself on: no HTTP, no timeouts, no side effects. Just compute the next state.

My fruits reducer lives in src/app/store/reducers/fruit.reducer.ts. It starts as an empty list and updates state based on success actions: 

const initialState: ReadonlyArray<Fruit> = [];
export const fruitReducer = createReducer(
    initialState,
    on(FruitsActions.getFruitsSuccess, (state, fruits) => fruits),
    on(FruitsActions.addFruitsSuccess, (state, fruits) => {
        return {...state, ...fruits}
    }),
    on(FruitsActions.updateFruitsSuccess, (state, fruits) => {
        return {...state, ...fruits}
    }),
    on(FruitsActions.deleteFruitsSuccess, (state, fruits) => {
        return fruits
    })
);

A real “learning moment” buried in this reducer

You can see the reducer returns arrays in some places and spreads arrays into objects in others ({...state, ...fruits}). That’s one of those things you only notice once you start consuming store state in components and the shape feels off.

It’s not catastrophic, but it taught me quickly: the reducer is the source of truth for state shape, and if it’s inconsistent, the UI ends up compensating.

Step 4: Effects (where HTTP belongs)

Effects are where the app stopped feeling tangled.

All API calls go through SharedService: 

  getFruits(): Observable<Fruit[]> {
    return this.http.get<Fruit[]>(FRUITS_URL);
  }
  updateFruit(fruit:Fruit): Observable<Fruit[]> {
    return this.http.put<Fruit[]>(FRUITS_UPDATE_URL, fruit);
  }
  addFruit(fruit: Fruit): Observable<Fruit[]> {
    return this.http.post<Fruit[]>(FRUITS_ADD_URL, fruit);
  }
  deleteFruit(name: string): Observable<Fruit[]> {
    return this.http.post<Fruit[]>(FRUITS_DELETE_URL, {"name" : name})
  }

Then FruitEffects listens to actions and maps them into API calls + next actions.

Load fruits effect 

    loadFuits$ = createEffect(() => {
        return this.actions$.pipe(
            ofType(getFruits),
            mergeMap(() => this.sharedService.getFruits().pipe(
                map(
                    (fruits: Fruit[]) => getFruitsSuccess(fruits)
                ),
                catchError(err => of(getFruitsFailure(err)))
            ))
        )
    })

Add fruit effect 

    addFuits$ = createEffect(() => {
        return this.actions$.pipe(
            ofType(addFruits),
            exhaustMap((newFruit: Fruit) => this.sharedService.addFruit(newFruit).pipe(
                map(
                    (fruits: Fruit[]) => addFruitsSuccess(fruits)
                ),
                catchError(err => of(addFruitsFailure()))
            ))
        )
    })

Delete fruit effect 

    deleteFuits$ = createEffect(() => {
        return this.actions$.pipe(
            ofType(deleteFruits),
            mergeMap((fruitName: any) => this.sharedService.deleteFruit(fruitName['name']).pipe(
                map(
                    (fruits: Fruit[]) => deleteFruitsSuccess(fruits)
                ),
                catchError(() => of(deleteFruitsFailure()))
            ))
        )
    })

Why this structure felt “worth it”

Once effects exist, components stop needing to know anything about HTTP. The UI becomes mostly:

dispatch action
render observable state

That separation is the first time NgRx starts paying you back.

The pattern I walked away with (and keep reusing)

If I strip everything down to the mental checklist I now follow, it’s this:

Module wiring

  • register store slice and effects
  • enable devtools while building

Actions

  • request + success + failure for each async operation

Effects

  • listen for request action
  • call service
  • dispatch success/failure

Reducer

  • update state immutably based on success/failure

Components

  • dispatch intent
  • select state

That’s the whole NgRx lifecycle in a shape I can reason about.

Small improvements I’d make next (without changing the spirit of the project)

Even keeping this as a learning-focused project, there are a few lightweight upgrades that would tighten it up:

  • Keep state shape consistent in the reducer (array stays an array)
  • Use selectors to create an abstructin layer between component and state.
  • Use one consistent action payload style (usually props<{ ... }>())
  • Track loading and error in state so UI behavior is driven by state rather than timer-based delays

Those changes don’t “enterprise-ify” anything—they just make the NgRx flow cleaner and easier to extend.
